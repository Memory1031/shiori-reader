# Android 与 Windows 自动升级规划

状态：发布协议、签名、共享检查下载、更新页面与 Android 安装交接已实现，Android 系统安装验收通过，覆盖 Android 12（API 31）真机安装、恢复与本地 EPUB 数据保留；真实 GitHub Release 端到端联调待完成。Windows 采用已确认的 ZIP 便携版方案，在应用内下载并重启更新；应用交接、独立更新程序与恢复流程已实现，本机真实包升级验收通过。

## 用户体验

统一入口为「更多 → 关于与更新」，展示当前版本（含 beta 标识）、更新渠道、检查时间和更新说明。构建号用于内部升级判断。中文、英文文案使用应用语言资源。

第一版提供自动检查、提示、下载和安装交接；下载由用户点击启动。自动检查可关闭，前台启动后最多每 24 小时检查一次，手动检查随时可用。检查在应用就绪后执行；阅读中只显示轻量提示，回到首页后查看详情。下载失败保留重试入口和对应 GitHub Release 链接。

| 平台 | 更新流程 |
| --- | --- |
| Android | 发现更新 → 查看说明 → 下载 APK → 校验 → 用户确认安装 → 系统覆盖安装 → 下次打开确认新版本 |
| Windows x64 | 发现更新 → 查看说明 → 下载 ZIP → 校验 → 点击「重启更新」→ 保存并正常退出 → 独立更新程序替换文件 → 启动新版本 |

下载状态包括进度、取消、失败重试和「已下载，稍后安装」。下载缓存使用独立目录，与书籍、图片缓存分开管理。进程退出时结束当前下载；下次根据本地记录识别并重新校验完整包，未完成的包重新下载。

## 版本与渠道

- 正式渠道只选择正式 Release；测试渠道同时接收 beta 和正式 Release。首次使用按安装包内的渠道标记设置，用户选择后持久化。
- 标签沿用 `vX.Y.Z` / `vX.Y.Z-beta.N`，每个版本的 beta 序号从 1 开始。安装版本保持 `X.Y.Z+build`；应用内显示完整发布标签，避免同版本多个 beta 难以区分。
- 更新候选必须匹配应用 ID、平台和架构，基础版本不低于当前版本，内部构建号严格大于当前构建号。比较数值，不能按字符串或发布时间直接决定更新。
- 构建号跨正式、beta 和平台持续递增。正式发布接续 beta 时，也分配新的构建号，即使 `X.Y.Z` 相同。
- 从测试渠道切回正式渠道只修改候选范围；若当前 beta 的构建号较高，等待符合条件的新正式包。界面说明等待状态，保留现有数据。
- 发布包嵌入 tag、channel、version、build、commit；本机运行时读取实际包版本并核对这些字段。调试运行、缺少发布身份的包及开发数据环境禁用在线更新；隔离测试通过显式注入测试服务执行。

## 发布源与更新清单

沿用 `Memory1031/shiori-reader` 的 GitHub Releases。发布工作流在 Android APK 与 Windows ZIP 均验证成功后生成 `update-manifest.json` 和独立签名，一起上传到对应 Release。

客户端已配置此仓库作为正式发布源。带有效发布身份和更新公钥的 release 构建，在生产数据环境中核对实际版本通过后启用更新；仅运行 `flutter build --release` 不足以启用。beta 包与正式包使用同一发布源，通过更新渠道筛选候选。

第 6 项负责正式发布源的端到端验收：先完成隔离测试，再使用获授权、由发布工作流生成的两个构建号递增的 beta 发布，验证 Android / Windows 从基线包发现新版、下载验签、安装及重启后数据保留的完整流程，同时验证正式渠道过滤 beta。客户端地址与开发包开关已由上述规则确定，这一步验收实际发布资产与客户端能否协同工作。

清单 v1 至少包含：协议版本、应用 ID、发布标签、渠道、基础版本、构建号、提交 SHA，以及各平台资产的名称、字节数、SHA-256、系统要求。Android 附带签名证书摘要；Windows 附带程序文件清单、每个文件的摘要和最低更新程序协议版本。

安装包和独立更新程序内置更新公钥，验证清单原始字节的签名后才接受资产信息。签名采用 RSA-3072 / PKCS#1 v1.5 / SHA-256：Dart 使用 PointyCastle，Windows 使用系统 CNG；CI 私钥使用独立发布 Secret。SHA-256 用于检查下载完整性，清单签名用于验证发布者身份。Android 的系统安装签名校验继续生效。配置方式见[发布操作](README.md#更新清单签名配置)。

通过 Releases 列表发现候选，过滤草稿及不符合渠道的发布，再读取清单；测试渠道需要包含预发布，不能只使用 latest 接口。分批、有界地读取列表，缓存响应及 ETag；达到扫描上限仍未得到可靠候选时提示暂时无法确定，不能误报已是最新版。处理限流、超时、离线和资源尚未上传完整等状态。应用使用公开接口，凭据留在发布环境中。

下载入口绑定官方仓库的指定 Release / asset；按 HTTPS 重定向规则兼容 GitHub 实际资产域名，限制跳转次数、清单大小和包大小。更新说明使用限高的原生 Markdown 预览，不加载图片、不执行 HTML、不响应文内链接；完整说明通过独立的受限发布页入口查看。仅在资产及签名都齐全后显示可安装更新。

已公开的同一标签 / 构建号对应固定内容。工作流重跑核对已有摘要：内容相同可补齐资产，内容变化需分配新构建号及新标签，避免客户端缓存指向不同包。

## Android 安装

基于当前 GitHub 签名 APK 分发方式，在原生桥接层接入 `PackageInstaller`。保持 `dev.shiori.reader` 和现有签名身份，以覆盖安装保留书架、阅读进度、原件与设置。

1. 下载到应用私有更新目录，验证清单签名、包大小、SHA-256、包名、构建号和签名身份。
2. Android 8+ 检查 `canRequestPackageInstalls()`；首次需要时解释用途，打开当前应用的「允许安装未知应用」设置，返回后重新检查。Android 7 使用相应系统安装流程。
3. 创建安装 session，写入 APK 并提交；收到 `STATUS_PENDING_USER_ACTION` 后展示系统确认界面。用户取消或拒绝权限时回到可重试状态。
4. 在进入安装前保存更新记录和阅读位置；下次启动根据实际安装版本确认完成并清理旧下载。

权限和 session 生命周期由 Android 层负责；共享 Dart 层消费进度和封闭结果。系统作为最终安装权限、签名及兼容性判定方。后续其他分发渠道可提供对应安装适配器。

恢复时先核对实际安装版本，再检查本应用拥有的 session：实际版本已达到目标则标记 `installed`；session 已不存在则允许重试；尚未 sealed 的 session 清理后允许重试；已 sealed 的 session 保留 `installing`，避免取消已提交的安装。API 26+ 使用 `SessionInfo.isSealed`，API 24／25 使用兼容检查；验收代码也遵守相同 API 可用性边界。

### 设备验收范围

Android 系统安装验收已通过。Android 7（API 24／25）不纳入本轮必测范围，不作为验收阻断项；现有兼容代码与最低系统版本要求保持不变。

- Android 12（API 31）真机已验证包元数据校验、错误签名拒绝、安装权限拒绝、未提交 session 清理、重新发起安装和取消、同版本更高构建号覆盖安装，以及新进程中的实际版本与 `installed` 状态识别。
- 已验证完整的跨进程保留场景：持久化 `installing` 且尚未 commit 时，由系统 `am crash` 终止应用；旧进程消失后 session 仍存在，新进程恢复时清理成功。该设备拒绝应用身份下的 SIGKILL，因此这不代表 SIGKILL 脚本验收通过。
- 覆盖安装前后，现有书架、阅读位置和设置比对一致。本地 EPUB 样本已覆盖：导入原件与解析资源保持逐字节一致，升级后可继续阅读并恢复到原正文页。
- 通用 runner 未自动识别华为额外的安装安全提示页；该步骤通过操作系统确认界面完成，不能计为 runner 全自动通过。不得通过关闭全局安全保护完成验收。
- 上述使用本地同签名测试包，覆盖的是 Android 安装与恢复链路，不包含真实 GitHub Release 发现、下载、内置公钥验签或渠道过滤。

设备验收入口为 [UpdateInstallSmokeRunner](../../android/app/src/androidTest/kotlin/dev/shiori/reader/UpdateInstallSmokeRunner.kt)，仅在显式指定 mode 时执行。`confirm` 交给系统安装，安装完成后再运行 `installed`，核对实际版本、构建号和生产安装状态；用户数据保留需另外比对，不能仅凭该断言推定。

[进程恢复脚本](../../tool/test_android_update_recovery.py) 的 `--require-retained` 要求 session 确实跨进程保留；若系统自动清理 session，不得算作保留会话恢复通过。设备拒绝终止命令时需另行验证真实进程死亡，并明确记录终止方式，不能以同进程内清理测试替代。

## Windows 便携版更新

随 ZIP 提供小型原生更新程序，与 Flutter 应用一起构建。它从安装目录之外的专用暂存目录运行，使用结构化任务文件交接，避免依赖 PowerShell 执行策略或动态拼接命令。

### 替换前

- 确认安装目录为本地可写目录，检查剩余空间、当前 EXE 身份、目标包身份和更新程序协议；不可原位更新时展示下载 / 解压新目录的入口。
- 主程序与更新程序协调同一安装目录的互斥锁，检查多实例占用。
- 验证签名并完整解压到独立目录。拒绝绝对路径、目录穿越、符号链接 / junction、重复或大小写冲突路径，以及超限解压内容；逐文件核对清单。
- 在目标卷准备暂存文件、备份和持久事务记录。仅管理当前和目标程序清单覆盖的文件，保留安装目录中的其他文件；首次启用时为程序包生成完整文件清单。

### 退出与替换

用户点击「重启更新」后，等待导入 / 数据写入等操作完成，保存阅读进度与设置，释放 SQLite、媒体及 WebView 资源。独立更新程序通过进程句柄等待对应实例退出；超时返回可诊断的失败状态，由用户关闭占用后重试。

按事务记录备份并替换程序文件，清理新版本不再使用的旧程序文件，再启动新 EXE。替换失败时恢复旧程序文件；事务记录支持更新程序再次运行时恢复未完成事务。需验证中途终止、磁盘不足和文件锁等故障下不会留下新旧 DLL 混用的可启动目录。

程序替换与数据迁移分别处理：自动文件回滚适用于新应用尚未开始数据迁移的阶段。新版本进入数据迁移后发生故障，保留更新记录与备份并走数据恢复流程，避免直接用旧程序读取新 schema。数据库升级继续遵守现有迁移约定。

更新程序的写入范围限定在经过校验的程序目录和自己的暂存 / 备份目录。书籍、SQLite、设置及缓存仍使用现有 `AppPaths`，从程序替换流程中隔离。

## 官方依据

- [Android PackageInstaller](https://developer.android.com/reference/android/content/pm/PackageInstaller)：安装 session、用户确认和结果状态。
- [Android PackageManager](https://developer.android.com/reference/android/content/pm/PackageManager#canRequestPackageInstalls())：未知来源安装授权检查。
- [GitHub Releases API](https://docs.github.com/en/rest/releases/releases)：发布列表、预发布和资产信息。
- [GitHub API 限流](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)：公开接口请求预算。
- [Windows 文件替换](https://learn.microsoft.com/en-us/windows/win32/fileio/moving-and-replacing-files)：原生文件移动与替换能力；完整包事务由更新程序协调。
